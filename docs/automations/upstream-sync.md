# Automation prompt — Sync MonoCode upstream

Source of truth for the **Sync MonoCode upstream** automation in Vatra (Tuesday and Friday, 09:00,
`claude:opus`, effort medium, worktree mode). After changing this file, paste everything below the
line into the automation's prompt.

Tooling it relies on: `scripts/upstream/apply.mjs` (per-path patch, exit codes 0/2/3/4),
`scripts/upstream/moves.mjs` (move map generate / `--check`), `.github/upstream-moves.json`.

---

You are running a scheduled upstream sync for Vatra (`deluminor/vatra`), a standalone repository derived from MonoCode (`hardbeat920/monocode`). Vatra is no longer a GitHub fork, so GitHub cannot sync it; this automation does it with plain git.

## Branch model
- `upstream/main` — MonoCode's default branch (remote `upstream`).
- `origin/upstream-main` — read-only mirror of `upstream/main` kept on our repo. Only ever fast-forwarded.
- `origin/main` — Vatra's product branch. Protected by a ruleset: changes land only through pull requests. It shares **no commits** with MonoCode: its history was reset to a single Vatra commit so that the repository's contributors are Vatra's own. Upstream changes are therefore applied as **patches**, never merged.
- `.github/upstream-sync.json` (on `main`) — `syncedCommit` is the last MonoCode commit whose changes are in `main`.

## Goal
1. Fast-forward `origin/upstream-main` to `upstream/main`.
2. Apply the changes between `syncedCommit` and `origin/upstream-main` to `main` through a pull request that builds, passes checks, keeps every Vatra feature and branding, and brings in every upstream change — with English release notes describing what changed.

The default outcome is a ready-to-review PR. A "Sync blocked" Issue is the exception, used only under the conditions in step 4c.

## Hard rules
1. Work only in this repository. Do not touch unrelated repos.
2. Never force-push. Never push to `main`. The only direct push to a protected ref allowed is a fast-forward of `upstream-main`.
3. Never `git merge`, `git cherry-pick`, `git rebase` onto, or otherwise bring MonoCode commits (anything reachable from `upstream-main` or `upstream/main`) into a Vatra branch, with or without `--allow-unrelated-histories`. It would add every MonoCode author back to Vatra's contributors. CI rejects such branches. Upstream content arrives only through `node scripts/upstream/apply.mjs`.
4. Never push or open PRs to `hardbeat920/monocode`. `gh` commands must target `deluminor/vatra` (pass `-R deluminor/vatra`).
5. If there is nothing new to sync, exit silently: no PR, no Issue, no extra commits.
6. Never commit conflict markers.
7. Never bypass git hooks: no `--no-verify`, no `-c core.hooksPath=...`, no hook-disabling env vars. If a hook fails, fix the cause.
8. Release notes must be written by you after reading the actual diff — not a raw dump of `git log`. Language: English.
9. Always attach the full notes to both a GitHub Issue and the PR description. Cross-link them.
10. No authorship or tool attribution in PR or Issue titles, bodies, comments, or automation-created commit messages. Never append signatures, badges, links, or trailers such as `Made with Cursor`, `Generated by AI`, `Created by an agent`, `Co-authored-by: Cursor`, or any equivalent mention that an agent, AI model, assistant, or tool authored the work. Technical descriptions of agent-session product features are allowed; do not remove legitimate feature documentation or rewrite upstream history. Both Cursor CLI settings `attributeCommitsToAgent` and `attributePRsToAgent` must remain disabled.
11. Never drop functionality from either side to make a conflict go away. Losing a Vatra feature or an upstream change is a defect.

## Steps

### 1. Preconditions
- Confirm `gh auth status` works.
- Ensure the `upstream` remote exists and points to MonoCode; add it if missing:
  ```bash
  git remote get-url upstream || git remote add upstream https://github.com/hardbeat920/monocode.git
  ```
- Fetch:
  ```bash
  git fetch origin main upstream-main
  git fetch upstream main
  ```
- Work from a fresh branch based on `origin/main`; do not dirty the user's WIP.
- Check that the patch-sync tooling is on `main`: `git cat-file -e origin/main:scripts/upstream/apply.mjs && git cat-file -e origin/main:.github/upstream-sync.json`. If either is missing, stop. Report only the one-liner `Patch-sync tooling is not on main yet; sync skipped.` Do not merge, do not open a PR or an Issue.
- Check the repository's git identity and state before any commit. `git config user.name` / `git config user.email` must be the owner's identity: never `CRLF Test`, and never an `@example.invalid` address. `git config --get core.bare` must be `false`. If any check fails, the repository config was corrupted by a test fixture. Stop and open a `Sync blocked: repository git config corrupted (YYYY-MM-DD)` Issue listing the bad keys. Do not repair the config yourself and do not commit.

### 2. Refresh the mirror
- If `origin/upstream-main` equals `upstream/main`, continue to step 3.
- If `origin/upstream-main` is an ancestor of `upstream/main`, fast-forward it:
  ```bash
  git merge-base --is-ancestor origin/upstream-main upstream/main
  git push origin upstream/main:refs/heads/upstream-main
  git fetch origin upstream-main
  ```
- Otherwise MonoCode rewrote history. Do not force-push. Open an Issue titled `Sync blocked: upstream-main diverged from MonoCode (YYYY-MM-DD)` describing both heads, then stop.

### 3. Divergence check and open sync PRs
```bash
SYNCED=$(git show origin/main:.github/upstream-sync.json | node -e 'process.stdin.on("data", d => console.log(JSON.parse(d).syncedCommit))')
git merge-base --is-ancestor "$SYNCED" origin/upstream-main   # must succeed
git rev-list --count "$SYNCED"..origin/upstream-main
```
- If `syncedCommit` is not an ancestor of `origin/upstream-main`, MonoCode rewrote history: open `Sync blocked: upstream-main diverged from MonoCode (YYYY-MM-DD)` with both commits and stop.
- If the count is `0`, stop immediately. No PR, no Issue. Report only a one-liner that nothing needed syncing.
- Never use `origin/main..origin/upstream-main` for counting or notes: the histories are unrelated, so that range is all of MonoCode.
- Check for an open sync PR: `gh pr list -R deluminor/vatra --state open --json number,headRefName,url --jq '.[] | select(.headRefName | startswith("sync/upstream-into-main-"))'`.
  - Read that branch's `.github/upstream-sync.json`. If its `syncedCommit` equals `origin/upstream-main`, stop: report the existing PR URL only.
  - If it is behind, do not open a second PR. Check out its head branch, run `node scripts/upstream/apply.mjs` again (it continues from the branch's recorded commit; steps 4–6 apply), commit, push normally (no force), and update that PR's and its linked Issue's bodies with refreshed notes covering the full range from `main`'s `syncedCommit` to `origin/upstream-main`.

### 4. Sync branch + patch
- Date stamp `YYYYMMDD` (local). Branch `sync/upstream-into-main-YYYYMMDD`; if it already exists on `origin`, append `-2`, `-3`, …
- Create it from `origin/main` and apply the upstream patch:
  ```bash
  git switch -c sync/upstream-into-main-YYYYMMDD origin/main
  node scripts/upstream/apply.mjs origin/upstream-main
  ```
  It applies `git diff <syncedCommit> origin/upstream-main` to the working tree and index **one path at a time** as three-way patches, updates `.github/upstream-sync.json`, and prints JSON with `status`, the upstream `commits`, `conflicts`, `pending`, `retargeted` and `added`. Exit `0` = applied (or up to date), `2` = conflict markers left in the listed files, `3` = upstream history diverged (open the diverged Issue from step 3 and stop), `4` = pending ports were written (conflicts may also be present; handle both).
  - `retargeted`: upstream edits to paths Vatra renamed, already applied to the Vatra path through `.github/upstream-moves.json`. Treat them like any applied change (they can also appear in `conflicts`).
  - `pending`: upstream changes to paths Vatra split, removed, or moved without a map entry. They were **not** applied; each has its diff under `.upstream-pending/<from>..<to>/`. Step 4b-bis ports them.
  - `added`: new upstream files. Step 4b-ter adapts them to Vatra's structure.
  - `extracted`: paths that still exist but from which Vatra moved some declarations (types, helpers) into other modules; each lists `names` and `target`. When an upstream hunk touches one of those names, it conflicts or lands next to code that moved: port that part into `target` and keep the old location clean.
- In this prompt, "the range" means `<syncedCommit>..origin/upstream-main`, and "the upstream diff of a file" means `git diff <syncedCommit> origin/upstream-main -- <path>`. Before resolving anything, read `git log --oneline` of the range and the upstream diff of every conflicting file, so you understand what each upstream change intends.
- Vatra's structure differs from MonoCode's: Vatra split large modules into folders, renamed files to kebab-case (components stay `PascalCase.tsx`), moved workspace state into a Zustand store (`src/app/workspace/store/`) and stateful flows (`src/app/workspace/flows/`), and regrouped Rust modules into domain folders. `.github/upstream-moves.json` records every move: `renames` (old path → new path), `splits` (old path → `targets` + `notes` describing what went where), `extractions` (old path that still exists → declarations moved to other modules) and `removed` (old path → reason). Read it before resolving anything.

#### 4a. Vatra-owned paths — keep Vatra's side
See `docs/releasing.md` → Syncing from upstream.
- Version numbers in `package.json`, `package-lock.json`, `Cargo.toml`, `Cargo.lock`, `src-tauri/tauri.conf.json`: keep Vatra's version and identity (`productName`, `identifier`), but take MonoCode's other changes (new or bumped dependencies, config). For lockfiles run `git checkout --ours` and regenerate them with `npm install --package-lock-only --ignore-scripts` and `cargo metadata --format-version 1 >/dev/null`. Never hand-edit lockfiles.
- `pnpm-lock.yaml` exists only in Vatra (upstream has none), so it never conflicts and silently goes stale. Whenever the sync changes `package.json` dependencies, also run `pnpm install --lockfile-only --ignore-scripts`. Check that the diff only touches the changed dependencies.
- `CHANGELOG.md`: keep Vatra's history and Vatra's link references. Never take upstream's version sections or `hardbeat920/monocode` compare links. See step 6b for the `Unreleased` notes.
- `.github/workflows/release.yml`, `scripts/release/`
- `src/app/model/fork-policy.ts`, `plugins.updater` in `src-tauri/tauri.conf.json`
- `RELEASE_DOWNLOAD_BASE` in `src-tauri/src/remote_ssh.rs`, `src-tauri/src/remote_bootstrap.{sh,ps1}`
- Host names in `host/` (`~/.vatra-host`, `vatra-host`, `com.vatra.host`, `Vatra Host-<SID>`, the `host.vatra` capability)
- Product name and branding (`Vatra` must not regress to `MonoCode`), `README.md`, `NOTICE`, `LICENSE`. Upstream README sections that promote MonoCode (contributors badges, acknowledgments, MonoCode links) are not taken.

#### 4a-bis. License notices — always port upstream changes (mandatory, also on a clean patch)
MIT requires every copy to carry the copyright and permission notices, so an upstream notice change must never be dropped, even inside the Vatra-owned paths above.
- Check what upstream changed in this range:
  ```bash
  git diff "$SYNCED" origin/upstream-main --stat -- LICENSE 'LICENSE*' NOTICE 'NOTICE*' '**/LICENSE*' '**/NOTICE*' '**/COPYING*'
  git diff "$SYNCED" origin/upstream-main -U0 | grep -E '^\+.*(Copyright|SPDX-License-Identifier|Licensed under)'
  ```
- `LICENSE`: keep Vatra's text, and add every new or changed upstream copyright line next to the existing `Copyright (c) 2026 Nick` line. Never remove or reword an upstream copyright line or the permission text.
- `NOTICE`: keep Vatra's text, and add upstream additions (new third-party attributions, new notices) in substance.
- New third-party license files (for example a new `vendor/<x>/LICENSE`) and copyright/SPDX headers in source files: take them exactly as upstream has them. In the branding scan (4d), never rename names inside a copyright line or license text.
- If upstream adds **source files** under a license other than MIT (check headers and new `LICENSE*` files), or a new **dependency** under GPL, LGPL or AGPL, stop and open a `Sync blocked: license review needed (YYYY-MM-DD)` Issue listing the files and licenses. Do not apply that code. New dependencies under MPL-2.0 or Apache-2.0 are allowed, but name them under **Breaking / attention**. Their notices (and crates.io source links for MPL crates) are generated at build time.
- Record what you did under **Breaking / attention** (`License notices: unchanged`, or the exact additions).
- Shipping checks. Do not remove any of these when resolving conflicts in Vatra-owned files:
  - `build.license` in `vite.config.ts` (generates `THIRD-PARTY-NOTICES.md` in `dist`, which Tauri embeds);
  - `node scripts/licenses/rust-notices.mjs` in `beforeBuildCommand` in `src-tauri/tauri.conf.json` (generates `THIRD-PARTY-NOTICES-RUST.md`);
  - `bundle.copyright`, and the `LICENSE` / `NOTICE` entries in `bundle.resources`, with `tauri.linux.conf.json` and `tauri.windows.conf.json` removing only `macos/Assets.car`;
  - the `VATRA-LICENSE` / `VATRA-NOTICE` / `THIRD-PARTY-NOTICES.md` copies in `host/package.mjs`, and `writeNpmNotices` with `metafile: true` in `host/build.mjs`.
- If upstream copies third-party source into the codebase (a file with someone else's copyright header, or a file that says it is "derived from" or "adapted from" another project), add that full notice verbatim to `NOTICE` under "Third-party code included in Vatra's own source", because minification strips source headers from the shipped app. Also mention new product names or logos shown in the UI in the trademark paragraph of `NOTICE`.

#### 4b. Product code (`src/`, `src-tauri/src/`, `host/` outside 4a) — resolve by combining both sides
Resolve the conflict when both sides' intent is clear and they can coexist. Typical cases:
- **Imports.** Vatra keeps its imports sorted, so upstream import hunks often duplicate imports Vatra already has elsewhere in the file. For every symbol on the upstream side, check whether the file already imports it. Add only the missing ones, at the sorted position. Never import a symbol twice.
- **Additive changes on the same line or prop list** (both sides add a prop, argument, field, case, or effect): keep both.
- **Vatra renames vs upstream edits** (for example `MonoCodeCallRow` → `VatraCallRow`, `monocode` → `vatra` identifiers): apply the upstream edit (logic, formatting) using Vatra's names.
- **Vatra refactored a block that upstream changed** (for example Vatra extracted a helper and upstream added a call): keep Vatra's structure and port upstream's new behavior into it.
- **Upstream extracted code into a new module or hook**: take the extraction, and make sure the old inline copy does not survive next to the new call. Remove imports that become unused, and remove duplicate state, effects, or functions.

After resolving, check every resolved file:
- `git diff origin/upstream-main -- <path>` and `git diff origin/main -- <path>`. Every upstream hunk must be present (possibly adapted to Vatra names), and no Vatra-only behavior may have been lost.
- Grep the file for identifiers that upstream removed or moved in this range. They must not remain as dead or duplicated code.

#### 4b-bis. Pending ports (mandatory whenever `pending` is non-empty)
Every upstream change must land in Vatra. A pending port is a change the patch could not place automatically; you place it by hand.
- Read `.upstream-pending/<from>..<to>/manifest.json`. For each entry read its `.diff`, the upstream commits that touched the path (`git log --oneline <syncedCommit>..origin/upstream-main -- <path>`), and its entry in `.github/upstream-moves.json`.
- Find where the touched code lives now. Start from the split `targets` and `notes`; then search the Vatra tree for the functions, components, state names, hooks or strings in the hunk context (`rg`, codegraph). Code that lived in `Workspace` (`src/app/App.tsx` upstream) is now in store slices, `flows/` modules, hooks or `ui/` components; follow the notes.
- Port the intent of every hunk into the new location, in Vatra's form: store actions instead of `setState` in `Workspace`, selectors instead of props, Vatra names, kebab-case file names. Do not paste the upstream block back as a monolith, and do not recreate a removed file.
- By reason:
  - `split`: port into the listed targets (new helpers go into a fitting module of the same folder or a new one next to it).
  - `removed`: the notes say why the file is gone and what replaced it. Port behaviour changes into the replacement; if the upstream change only touches code that no longer exists and has no behavioural effect in Vatra, record it as **Not applicable** with the reason.
  - `unmapped`: Vatra moved or deleted the path without a map entry. Locate the code; if it is a 1:1 move, also add the rename to `renames` in `.github/upstream-moves.json`.
  - `moved-and-renamed-upstream`: upstream renamed a file Vatra had already moved. Keep Vatra's path (`vatraPath`), port the content changes, and update the map entry if upstream's new name should map there from now on.
  - `apply-failed`: read `error`; usually binary or mode changes. Apply by hand.
- Ported code obeys the project checks (file size, layer boundaries, lint). If a target would grow past its size limit, split it the way neighbouring modules are split.
- Add or update tests when the upstream range changed tests for the ported code: port those test changes into the Vatra test that covers the new location.
- Never commit `.upstream-pending/` (it is ignored). Keep a list: every pending entry ends as **Ported** (with the Vatra paths), **Not applicable** (with the reason) or **Needs human** (with what blocks it).
- Pending ports never justify a blocked Issue on their own. When an entry needs a product decision, leave Vatra's code unchanged for that entry, open the PR anyway, and list it under **Needs human**. Add the `needs-human` label to the PR if the label exists; do not create labels.

#### 4b-ter. New upstream files (`added`)
- Rename each to Vatra's convention (`kebab-case.ts`; components `PascalCase.tsx`; hooks `use-*.ts`) and place it in Vatra's structure when its upstream folder no longer matches (for example a new `src/app/*` helper that belongs in `src/app/workspace/`). Fix its imports to Vatra's paths and the `@/` alias.
- When you rename or move an added file, record it in `renames` of `.github/upstream-moves.json` (upstream path → Vatra path) so later upstream edits are retargeted automatically.
- If an added file is oversized or mixes concerns, split it like the surrounding Vatra code and record it under `splits`.
- Run `node scripts/upstream/moves.mjs --check`; it must pass.

#### 4c. When to stop with a blocked Issue instead
Only when at least one of these holds:
- Both sides changed the same behavior in incompatible ways and keeping both is impossible without a product decision.
- You cannot tell what one side intends.
- After a reasonable effort to fix sync-caused errors (step 5), `tsc` or tests still fail in code touched by the conflict.

Then:
- Discard the attempt: `git reset --hard origin/main && git clean -fd` on the sync branch (it is local and was never pushed). Do not push the branch and do not open a PR.
- Open an Issue titled `Sync blocked: MonoCode → main needs human (YYYY-MM-DD)`, labeled `sync-notes` if the label exists. The body starts with a **Needs human** section that lists:
  - every conflicting path, each with a plain-language description of what each side did and the recommended resolution;
  - the decision that blocked you;
  - the range (`<syncedCommit>..origin/upstream-main`, with both hashes);
  - the local commands to reproduce: `git fetch origin && git switch -c sync/upstream-into-main-YYYYMMDD origin/main && node scripts/upstream/apply.mjs`.
  Include the release notes from step 6, with `Conflict status: Conflicts`.
- Stop.

#### 4d. Branding and naming scan (mandatory, also on a clean patch)
Upstream code that applies cleanly can still bring MonoCode names into Vatra. Scan the lines this sync adds:
```bash
git diff origin/main -U0 | grep -E '^\+' | grep -v '^+++' | grep -i monocode
```
Fix any hit that is a product identifier or user-facing text:
- `localStorage` / settings keys `monocode.*` → `vatra.*`
- Event names `monocode:*` → `vatra:*`
- `cli: "monocode"` and similar enum or literal values → `vatra`, unless Vatra's code still uses the legacy value on purpose (check how the same identifier appears in `origin/main`)
- Component, function, or type names containing `MonoCode` → the `Vatra` equivalent
- UI strings, window titles, menu labels, notifications, and prompts that say MonoCode → Vatra
- Paths and bundle identifiers (`~/.monocode*`, `com.monocode.*`) → Vatra equivalents

Leave these alone:
- Copyright lines, license texts, and attribution notices (`LICENSE`, `NOTICE`, `vendor/**/LICENSE*`, source headers). These must keep the original names.
- Links to upstream issues or PRs in comments (`github.com/hardbeat920/monocode/issues/NNN`)
- Code that intentionally handles legacy MonoCode data (`legacyStorageMigration`, profile import, `monocode.*` → `vatra.*` migrations)
- The `From MonoCode #NNN` references in `CHANGELOG.md`

Update tests that assert on renamed keys or names in the same way.

### 5. Verify
- `npm ci && npm run check:web` (vitest, `tsc --noEmit`, lint, file-size, layer-boundary and move-map checks).
- If the sync touched `src-tauri/` or `Cargo.*`, also run `cargo check --quiet` in `src-tauri/`.
- If the sync touched `host/`, also run `npm run test:host`.
- Sync-caused failures (unused or duplicate imports, a renamed symbol, a test asserting an old key) are your responsibility: fix them in the sync branch and re-run until green.
- If a failure is not caused by the sync (it also fails on `origin/upstream-main` alone, or on `origin/main` alone), still open the PR, and list the failures with their output under **Breaking / attention**.

### 6. Analyze changes and write release notes
Inspect at least:
- `git log --oneline "$SYNCED"..origin/upstream-main` (`$SYNCED` = `main`'s `syncedCommit`, see step 3)
- `git diff --stat "$SYNCED" origin/upstream-main`
- `git diff "$SYNCED" origin/upstream-main -- CHANGELOG.md`. Upstream's changelog describes user-visible behavior; use it as a source, but verify it against the code.
- Meaningful file diffs for user-facing or behavioral changes (UI, harness, git, sessions, automations, releases, remote host, settings defaults). Skip noise (lockfile-only, formatting-only) unless that is the whole change.

#### 6a. Notes format
```markdown
## Summary
2–4 sentences: what this sync brings into Vatra `main`.
## Highlights
- Meaningful changes (features, fixes, behavior), related commits grouped.
## Breaking / attention
- Changes that may break Vatra-owned parts, and migrations, config, or branding changes.
- User-visible default changes (settings defaults, privacy behavior, what is restored on restart, and similar), described in plain language: what the user sees today vs after the sync, and how to get the old behavior back.
- Renamed keys or identifiers from the branding scan.
- Check results: pass, or failures with output.
If none apply, write `None.`
## Upstream commits
- Commit subjects oldest → newest, max ~30; if more, show 30 and note the remainder.
## Conflict status
- `Clean patch`, or `Resolved` + every resolved path grouped as **Product code** / **Vatra-owned paths**, each with a one-line description of how it was resolved. Product-code resolutions must be specific enough for a reviewer to verify.
- **Retargeted**: upstream path → Vatra path, one line each.
- **Ported**: every pending entry as `upstream path → Vatra path(s)`: what was ported, one line each. **Not applicable** entries with the reason.
## Needs human
- Only when some pending entries or conflicts could not be ported: each with the upstream diff summary, where it would go in Vatra, and the decision needed. Omit the section otherwise.
```
Be specific and honest. Prefer outcomes over hashes. Do not invent changes.

#### 6b. Vatra `CHANGELOG.md` `Unreleased` entries (mandatory)
The release script (`scripts/release/prepare.mjs`) excludes every commit reachable from `upstream-main` from its generated notes, and combines the rest with `## [Unreleased]`. Without notes in `Unreleased`, the next Vatra release would silently omit everything this sync brings in. So in the sync branch:
- Add the user-visible changes from this range under `## [Unreleased]`, using Keep a Changelog sections (`### Added`, `### Changed`, `### Fixed`, `### Removed`). Merge them into any entries already there instead of duplicating sections.
- Base the entries on upstream's changelog wording, adapted for Vatra:
  - write `MonoCode #NNN` instead of a bare `#NNN` (a bare number would link to Vatra's own issues);
  - drop contributor handles and wording specific to MonoCode versions ("after upgrading from 0.6.0" → "after updating");
  - use Vatra branding.
- Only describe commits in the range. Everything before `syncedCommit` is already in `main`.
- Skip internal-only changes (tests, refactors, upstream release bumps, upstream README/docs).
- Keep the release tooling happy: run `npx vitest run scripts/release/` after editing.

### 7. Commit, push, PR, Issue
- Before every commit, run `git status --short` and `git diff --cached --name-only`. Only paths this sync intends to change may be staged. Never commit stray test fixtures (for example `notes.txt` at the repo root), scratch files, `.upstream-pending/`, or anything outside the patch, its conflict resolutions, the pending ports, `.github/upstream-moves.json`, the branding scan, `CHANGELOG.md` and the lockfiles. If unexpected paths are staged, unstage them and find out where they came from.
- Commit the sync as one commit with the message `chore(sync): apply MonoCode main <short syncedCommit>..<short new commit> (YYYY-MM-DD)`, and list the upstream commit subjects from `apply.mjs` in the body. If you resolved conflicts or made scan fixes, add a body line summarizing them. Commit any later fixes as separate conventional commits on the same branch (for example `fix(sync): rename display preference keys to vatra prefix`). Hooks must run (hard rule 6).
- Confirm the sync commit has exactly one parent (`origin/main`), that its author and committer are the owner's identity (`git log -1 --format='%an <%ae> / %cn <%ce>'`), and that the branch shares no history with MonoCode: `git merge-base HEAD origin/upstream-main` must fail. If it succeeds, the branch is contaminated: delete it locally and start over.
- `git push -u origin <sync branch>`. The repository's `pre-push` hook runs `npm run check:web`. Tests are isolated from the hook's git environment by `scripts/test/isolate-git-env.mjs`. If that file is missing from the checked-out tree, the hook's tests can rewrite this repository's config and commit fixtures. In that case stop before pushing and report it.
- After pushing, re-check `git config user.name`, `git config --get core.bare`, and `git log -3 --format='%h %an %s'` on the sync branch. No `CRLF Test` identity, no `Initial content` / `Remove file from index` commits.
- PR: `-R deluminor/vatra`, **base** `main`, **head** the sync branch, **title** `sync: MonoCode main into main (YYYY-MM-DD)`, **body** full notes + Issue link.
- Issue: `-R deluminor/vatra`, **title** `Sync notes: MonoCode → main (YYYY-MM-DD)`, **body** full notes + PR link. Label `sync-notes` if it exists; do not create labels.
- If a `Sync blocked: MonoCode → main needs human` Issue is open for the same commit range (for example, from an earlier run today), reuse it: retitle it to `Sync notes: …`, replace its body with the notes + PR link, and add a line saying the conflicts were resolved in the PR. Do not open a duplicate.
- Edit whichever was created first so both link to each other.
- Read `gh pr view -R deluminor/vatra <n> --json mergeable` back. If it is `CONFLICTING`, `main` moved during the run: merge `origin/main` into the sync branch (both are Vatra history, so this is allowed), resolve, re-verify, and push (no force).

### 7a. Verify publication text (mandatory)
